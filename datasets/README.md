# NovaBuild Dataset

**21 tables · ~76,500 rows · Date range: 2021–2024 · PostgreSQL 15**

The NovaBuild dataset is a **realistic synthetic simulation of commercial construction insurance operations**. Every module in this portfolio operates against this dataset — it is the substrate that makes each demonstration domain-authentic rather than toy.

The schema is deliberately modeled to align with **modern InsurTech operational platforms** — the same shape of data structures that power contractor prequalification, insurance certificate management, wrap program enrollment, claims intelligence, and executive risk analytics in production.

---

## Domain — What's Being Modeled

Commercial construction insurance is a domain where a single project can involve:

- **Dozens of contractors** across trades (concrete, electrical, mechanical, framing, roofing…)
- **Hundreds of insurance certificates** requiring weekly verification
- **Complex wrap programs** (OCIP / CCIP) enrolling contractors under a single insurance umbrella
- **Payroll audits** that determine actual premium exposure
- **Compliance tracking** across GL, WC, Auto, and Umbrella coverage lines
- **Claims lifecycle** from loss event → assessment → payments → subrogation

NovaBuild models this entire operational surface — the same data-flow patterns handled by platforms like **WrapPortal, Asuretify, Prequaligy, Anzenn, and modern claims-intelligence systems**.

## Realism Choices Baked In

The data is generated with deliberate realistic patterns — not uniform distributions:

- **Contractor tiers** (A/B/C/D) drive risk score, EMR, and prequalification outcomes
- **Payroll audits** show variance between reported and audited amounts (a real underwriting concern)
- **Certificates** have expiration cycles causing rolling compliance workflows
- **Claims** cluster by trade type and severity (electrical incidents skew high-severity, for example)
- **Wrap programs** have realistic enrollment counts (10–80 contractors per program)
- **Endorsements** and **premium adjustments** flow through the policy lifecycle authentically

These choices mean the dataset can meaningfully answer questions a real underwriter or risk manager asks — not just "count of X" but "which contractors have deteriorating risk trends over the last 6 quarters."

## How to Reproduce Locally

1. Provision a PostgreSQL 15 database
2. Run `schema.sql` to create the 21 tables
3. Run the Colab-style setup script to seed data (script arrives with Module 03 migration)
4. Verify with `SELECT COUNT(*)` — total should hit ~76,500 rows

Alternatively, connect to a Supabase-hosted instance if you want the data ready to go without local setup.

## Why This Dataset Matters for the Portfolio

Every DE portfolio uses *some* dataset. Most reach for **Chinook**, **Sakila**, **Northwind**, or **NYC Taxi** — well-worn public datasets with no domain story.

NovaBuild does two things those cannot:

1. **Domain alignment** — every table maps to a real InsurTech operational concern. A recruiter from a construction-insurance company or an underwriting platform reads this schema and immediately recognizes their own operations.

2. **Vertical depth** — the schema doesn't stop at "orders and customers." It goes into the workflows (payroll audit, certificate verification, compliance tracking, wrap enrollment) where actual business logic lives. That's what production DE work looks like.

The result is that every module downstream — the Pandas ETL, the SQL analytics, the Spark pipeline, the FastAPI service — is doing work that would make sense inside a real InsurTech company.
